4 · Routes — The API Surface

Every line of user_routes.js and file_routes.js — where URLs, middleware chains, and controllers get wired together. Small files, big lessons: ordering, rate limiting, and a famous space bug.

Before line 1: how routing works in Express

A router is a mini-app: it holds a list of route rules and matches incoming requests against them — method + path first, then in registration order. The first matching rule wins and its chain runs; nothing after it does.

server.js: app.use("/api/auth", userRoutes); ← mounts the router under a prefix app.use("/api/files", fileRoutes); so inside userRoutes: router.post("/login", …) …really means: POST /api/auth/login

The route chain is middleware composition. A rule like:

router.get("/users", auth_middleware, authorize("admin"), getUsers);

builds a conveyor belt: auth_middleware (verify token, attach req.user) → authorize("admin") (role check) → getUsers (business logic). Any link can terminate with a response; the controller at the end is just "the last middleware".

Reading a routes file = reading the API's public contract: every line answers "what can the outside world do, and what does it cost (auth? rate limit?) to do it?"

lines 1–20Imports + the router + the public trio


const router = express.Router();

router.post("/register", registerUser);
router.post("/login", loginUser);
router.post("/logout", auth_middleware, logoutUser);

    
What is itexpress.Router() creates the mountable mini-app; every rule below is relative to /api/auth (from server.js). The first two routes have no middleware — deliberately: you can't already be authenticated when registering or logging in. Logout, by contrast, runs auth_middleware first — it validates the token before clearing the cookie, so the endpoint doubles as an "am I really logged in?" check and a logout with a garbage cookie cleanly 401s.

    
Why POST for register/login/logoutREST semantics: these are actions, not resource reads — they change state (create a user, issue a cookie, delete a cookie). Browsers and caches treat GET as safe/idempotent; anything with side effects belongs in POST. The Google endpoints below are GETs — correctly, because they're navigations (the browser must follow redirects to Google and back; an XHR can't do that).


router.get("/google", redirectToGoogle);
router.get("/google/callback", googleCallback);
router.get("/me", auth_middleware, getMe);

    
How the OAuth pair wires up/google is the button's target: it 302s to Google's consent screen. /google/callback is the redirect_uri registered in Google Cloud Console — Google hard-codes its return trip here, with ?code=…&state=…. Both are public — no auth middleware, obviously: you can't be logged in yet; the entire point is to become logged in. And /me is the session-check endpoint the frontend calls on every load — cookie in, user object out.


router.get("/users", auth_middleware, authorize("admin"), getUsers);
router.get("/users/:userId", auth_middleware, authorizeUser, getUserById);
router.patch("/users/:userId", auth_middleware, authorizeUser, updateUser);
router.delete("/users/:userId", auth_middleware, authorizeUser, deleteUser);

    
Why two different guards on sibling routesThe four-line contrast worth reciting: /users (list everyone) is admin-only — authorize("admin") checks what kind of user you are. The /users/:userId trio is self-or-admin — authorizeUser checks whose row you're touching. Route-level (role) vs object-level (ownership) authorization, expressed as two middleware on neighboring lines. And the method spread — GET/PATCH/DELETE on the same path — is REST in miniature: same resource, different verbs, different powers.

    
Also noticePATCH for partial updates (send only changed fields) vs PUT (full replacement) — this API correctly chose PATCH since updateUser accepts any subset. And no POST /users exists — creation happens via /register, which is the right call (one public path into the users collection).

  


  

    
patternThe guard sandwich — the recurring shape


router.get("/me", auth_middleware, getMe);

    
Why it mattersRead every line of this file as: [who may call this?] + [what runs]. Zero guards = public. One guard = authenticated. Two guards = authenticated AND authorized. The chain is the access-control policy, visible at a glance — no policy hidden inside controllers (though updateUser/deleteUser re-check ownership defensively — belt and suspenders). If an interviewer asks "where is your authorization logic?", the honest answer is "mostly in the route declarations; duplicated defensively in two handlers."

Walkthrough — every line


  

    
lines 31–38guestUpload — a second, stricter Multer instance


const guestUpload = multer({
    storage: multer.memoryStorage(),
    limits: { fileSize: 25 * 1024 * 1024, files: 3},
    fileFilter: (req, file, cb) => {
        const ALLOWED = ['image/jpeg', 'image/png', 'application/pdf', 'text/plain'];
        ALLOWED.includes(file.mimetype) ? cb(null, true) : cb(new Error("Only JPEG, PNG, PDF, and TXT…"));
    }
})

    
Why a second instance instead of reusing uploadGuest uploads are the abuse surface — anonymous users, no quota, no account. So the policy tightens: 25MB (half the registered cap), fewer files, and a four-type whitelist (images/PDF/text — no audio/video) versus the registered fifteen. Same library, different policy object — the multer-as-config pattern again. The ternary in the filter is the compact form of the registered version's if/else; same semantics.

    
Found while reading — three drift points(1) limits: { files: 3 } but the route calls guestUpload.array("files", 5) — Multer's route-level cap (5) overrides/behaves inconsistently with the instance cap (3); the README claims 3. Drift in three places — the instance config wins on size, the route wins on count. (2) The controller's own GUEST_MAX_FILE_SIZE = 50MB re-check is dormant — Multer rejects at 25MB long before. (3) No storage override would have been needed anyway (multer defaults to memory), but declaring it explicitly documents intent. Three sources of truth for one policy = the textbook case for extracting guest limits to one constants module.

  


  

    
lines 40–46passwordRateLimit — brute-force protection


const passwordRateLimit = rateLimit({
    windowMs: 15 * 60 * 1000,   // 15 minutes
    max: 10,                     // 10 attempts per window per IP
    message: { message: "Too many attempts, please try again later"},
    standardHeaders: true,       // RateLimit-* headers for clients
})

    
What is itAn express-rate-limit middleware — the factory pattern again (configure → returns middleware). Per client IP, it allows 10 password verifications per 15-minute sliding window; attempt 11 gets the JSON message with 429. standardHeaders adds RateLimit-Limit/Remaining/Reset headers so well-behaved clients can self-throttle.

    
Why it's attached exactly where it isIt's mounted on the three verify-password routes — the only endpoints where an attacker can test guesses against a secret. Brute-forcing a bcrypt-protected file password is hopeless if you get 10 tries per quarter hour: 4 guesses/hour vs bcrypt's own slowness. Note the honest limitation: the default store is in-memory per process — restarts wipe counts, and horizontal scaling (multiple instances behind a load balancer) gives attackers N× the budget. The production answer: a Redis store (rate-limit-redis) shared across instances — which this app conveniently already runs.

    
Interview soundbite"Public password checks get two layers: bcrypt makes each guess expensive, the rate limiter makes guessing slow — 10 per 15 minutes per IP. And I know its default store is per-process memory, so multi-instance deployments need the Redis store."

router.get("/my-files", auth_middleware, showUserFiles);
…

How to read the four groups
      

        
GroupRoutesPattern to notice

        
Core file ops/upload, /my-files, /searchUpload chains three middlewares: auth → multer → controller. Multer sits after auth (why parse 50MB for a request that would 401?) and before the controller (bytes must exist when it runs) — middleware order is load-order engineering.

        
Reads & analytics/details/:fileId, /download-info/:fileId, /download/:fileId, /download-count/:fileIdAll auth'd — reads are still user-scoped. download-info vs download split: lightweight metadata page-load vs actual gated retrieval.

        
MutationsDELETE /delete/:fileId, PATCH /status|expiry|password/:fileId, PATCH /expiry-allOne mutation per endpoint (REST-ish action naming). Note /expiry-all is a PATCH on a collection, not an item.

        
Sharing/share-link/:fileId, /send-email/:fileId, /qr/:fileIdOwner-only conveniences; the public consumption side lives in the next group.

        
Public surface/share/: slug (broken), /verify-password/:fileId, /verify-password/:slug, /guest/*No auth middleware — by design. These are what a stranger with a link can touch. This is exactly why the password-verify trio gets the rate limiter and the guest upload gets its own multer.

      

      The upload route is worth reciting in interviews: auth_middleware → upload.array → uploadFiles — "verify identity before paying the parse cost, parse bytes before the handler needs them."

  


  

    
line 70The space bug — proven with a live test


router.get("/share/: slug", resolveShareLink);
//                          ↑ a SPACE inside the param name

    
Found while reading — and reproducedThis was verified by running a minimal Express app with this exact route against the server's own Express install:

      app.get('/share/: slug', …) → registered: true → GET /share/abc123 → 404

      Express accepts the route definition without complaint, but the route never matches any real request — the parameter name is parsed with the space and real URLs don't match. Net effect in production: GET /api/files/share/<slug> — the endpoint the React shared-file page calls — always 404s. Combined with the phantom shortUrl field (controllers page), the registered-file sharing flow is broken end-to-end, invisibly: every piece returns a well-formed response or a clean 404, never a crash. Fix: "/share/:slug" — delete the space. This is the single most quotable finding in the project: "a one-character bug that silently disabled a feature, found by reading and proven with a two-line test."

  


  

    
lines 72–78Duplicate routes + the param-name mismatch


router.post("/verify-password/:fileId", passwordRateLimit, verifyFilePassword);
router.post("/verify-password/:slug", passwordRateLimit, verifyFilePassword);
…
router.get("/guest/download-info/:shortUrl", guestDownloadInfo);

    
How duplicate paths resolveExpress matches in registration order: /verify-password/abc123 hits the first rule, binding the value to req.params.fileId — and the handler reads req.params.fileId, so it works. The second rule is dead code: identical pattern (same URL shape — the param name doesn't change matching), never reached. It reveals intent drift: someone planned slug-based verification (matching resolveShareLink's slug world) and left both. Since the handler only knows fileId, the slug variant could never have worked without rewriting the handler anyway.

    
Found while reading — the guest 404 machineThe route binds :shortUrl; the controller destructures { slug } = req.params → slug is undefined → GuestFile.findOne({slug: undefined}) matches nothing → every guest download-info request 404s. The guest share page can never display file metadata in production. One-word fix: rename the param to :slug. Route names and controller destructuring are a contract — nothing checks it for you.

    
Also notice/guest/upload has no rate-limit middleware — its abuse protection is the controller's DB-backed count (5/24h per IP), not express-rate-limit. Two rate-limiting mechanisms in one app, chosen per-context: memory-based for request-flood protection (password guesses), DB-backed for identity-less budget enforcement (guest uploads). Being able to explain when each fits is a genuinely senior answer.

  







  
Interview questions this folder invites


  

    
"How does Express decide which route handles a request?"

    
"Method + path match, then registration order — first match wins and later rules never run. That's why my two /verify-password routes behave the way they do: the :fileId one always wins, and the :slug one is unreachable. Route order is behavior."

  


  

    
"Why is Multer after auth but before the controller on /upload?"

    
"Cost and dependency ordering: auth is a cheap string verification — reject unauthenticated uploads before paying to parse megabytes. And the controller needs req.files to exist, so parsing must finish first. Middleware order is both a security and a performance decision."

  


  

    
"How do you protect a public password-check endpoint from brute force?"

    
"Two layers: bcrypt cost (each guess is CPU-expensive) plus express-rate-limit at 10 attempts per 15 minutes per IP with standard headers. And I know the default store is in-memory per process — for multi-instance production I'd swap in the Redis store, which my stack already has."

  


  

    
"Tell me about a bug you found in your own code."

    
"My favorite: router.get('/share/: slug', …) — a space inside the parameter name. Express registers the route happily but it never matches a single request; I reproduced it with a two-line test against my own Express install and got a 404. A one-character bug that silently disabled the whole share page — which is exactly why I now read routes and controllers as a matched contract."

  


  

    
"Where is authorization enforced in your API?"

    
"Structurally, in the route declarations — each line declares its own guards, from none (public guest endpoints) to auth-only to auth+admin. Object-level checks (whose file?) live in authorizeUser middleware for /users/:userId and are re-checked defensively inside file handlers. The route file reads as the API's access-control policy."
